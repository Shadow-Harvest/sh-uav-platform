## 📚 Key Concepts Learned

### 1. What is MAVROS?

MAVROS is a **translator/bridge** between ROS2 and the flight controller:


Your ROS2 Code ←→ MAVROS ←→ Flight Controller (ArduPilot)
(topics) (bridge) (MAVLink protocol)

- Converts ROS2 topics/services to MAVLink messages
- Bidirectional: sends commands, receives telemetry
- Key topics:
  - `/mavros/state` - arm status, mode, connection
  - `/mavros/local_position/pose` - current position
  - `/mavros/setpoint_position/local` - position commands

---

### 2. What is GUIDED Mode?

Flight controllers have multiple modes determining who controls the drone:

| Mode | Controller | Use Case |
|------|------------|----------|
| STABILIZE | Human pilot | Manual flying |
| LOITER | Drone | Hold position |
| AUTO | Pre-programmed | Waypoint missions |
| **GUIDED** | **External computer (us!)** | **Autonomous via ROS2** |
| RTL | Drone | Return to launch |

**GUIDED mode** = "I'll accept commands from an external computer"

**Critical:** Must keep sending setpoints (>2Hz) or drone triggers failsafe.

---

### 3. Services vs Action Servers

| Aspect | Service | Action |
|--------|---------|--------|
| **Duration** | Milliseconds | Seconds to minutes |
| **Blocking** | Client waits | Client continues |
| **Feedback** | None | Periodic updates |
| **Cancellation** | No | Yes |
| **Use when** | Quick command (arm, set_mode) | Long task (takeoff, land) |

**Action structure:**

Goal - what client requests
Result - final outcome
Feedback - periodic updates during execution

---

### 4. Setpoint Streaming

**What is a setpoint?** "Where I want to be" or "how I want to move"

- **Position setpoint:** Go to (x, y, z)
- **Velocity setpoint:** Move at (vx, vy, vz)

**Why 20Hz?**
- Flight controller expects constant communication
- No setpoint for 500ms = "computer crashed!" → failsafe triggers
- Even hovering requires repeatedly saying "stay here"

**Analogy:** Dead man's switch - must keep pressing to prove you're conscious.

---

### 5. GPS-Denied Flight (Bonus Learning)

Discussed how flight works without GPS:

- EKF (Extended Kalman Filter) fuses multiple sensors
- IMU, barometer, optical flow, visual markers
- ArUco markers can provide position reference (what our project builds toward!)
- Our code doesn't change - EKF handles sensor fusion, we just use `/mavros/local_position/pose`

### 6. Why Actions Live in `uav_msgs`

**.action files are interfaces (contracts), not implementations**


uav_msgs (interfaces) ← Both depend on this
↑ ↑
uav_control uav_mission
(server) (client)

- `uav_control` implements action servers (does the work)
- `uav_mission` calls actions as client (uses the work)
- Both need the interface definition
- Putting in `uav_msgs` avoids peer dependencies (bad practice)

**Same logic as .msg files:**
- Interface = shared contract
- Implementation = separate packages

## 💡 Key Insights

### 1. Separation of Concerns in Actions

My initial designs considered combining takeoff+navigation or land+navigation.

**Correct approach:** Keep them separate (single responsibility).
- Takeoff = pure vertical ascent
- Navigation = separate action/behavior
- Land = pure descent

### 2. Timeout as Safety Feature

Adding `timeout_sec` to actions is professional practice:
- Prevents infinite waiting if something fails
- Allows graceful failure handling
- 0 = no timeout (optional)

### 3. success + message Pattern

```python
# Bool for code to check (machine-readable)
if result.success:
    ...

# String for humans to read in logs
self.get_logger().info(result.message)

Similar to HTTP: status code (200) + body (details).
4. Interface vs Implementation
.msg    = data structure interface
.srv    = request/response interface  
.action = long-running task interface

All are CONTRACTS, not implementations.
All belong in shared msgs package.
